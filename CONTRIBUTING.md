# Contributing to punchcutter

Thank you for looking. The rules below are the ones the engine's design
depends on, and each says why it exists.

## Where a change goes

**GPU first.** The CPU does I/O: reading a font file, finding fonts through
fontconfig, writing a cache. Any computation over data the GPU can hold
belongs in a Slang module under `slang/modules/`. That includes shaping,
coverage, table walks and any decision about a glyph. Nothing on the CPU side
reads a lookup, a coverage table or a subtable format, and there is no CPU
shaper, not even a reference one, because a second implementation is a second
set of answers. If you think something cannot be done in the shader, say why
in the pull request.

**The engine knows nothing about its consumer.** No module or crate assumes
what is drawing the text, which descriptor sets a host uses beyond the curve
buffers' set 1, or when it shapes.

## Languages and layouts

- **Slang, not WGSL**, for every shader. Shaders are compiled to SPIR-V by
  Slang in process (`punchcutter-slang`) and loaded through wgpu's
  passthrough.
- **Shared layouts are declared once, in Rust.** The arena and the shaping
  dispatch are declared in `shape/src/abi.rs` through
  `punchcutter_core::decl`. `slang/modules/shape_abi.slang` is generated by
  `cargo run -p punchcutter-shape --bin gen-slang` and checked in. Never edit
  it by hand. A test fails when the file on disk differs from the rendering,
  and another compares every struct's offsets with Slang's reflection. The
  curve buffers in `text/src/layout.rs` are mirrored by hand in
  `slang/modules/text.slang` and checked by the same kind of reflection test.
- **Every field of a shared struct is a `uint`, an `int`, a `float` or an
  array of them.** No 3-vectors: std430 aligns them to 16 bytes
  (docs/arena.md, *Layout rules*).
- **Untrusted bytes are bounded.** A font is a file the engine does not
  control. Every read from the arena is clamped to what was bound, and every
  list a table declares is capped and charged against the operation budget
  before its first iteration. Do not make a budget charge a loop's exit
  condition; one driver miscompiled exactly that (`faceFor` in
  `slang/modules/shape.slang` explains).

## Licensing

The engine is MIT. Code brought in from elsewhere must be under a compatible
licence, keep its own notice where it lands (see the header of
`slang/modules/text.slang` for an example), and be listed in `NOTICE`.

## Dependencies

`Cargo.lock` is committed and is the source of truth. Build and test with
`--locked`.

Never run a bare `cargo update` or `cargo add`. Every change to the lockfile
goes through a release-age cooldown using `cargo cooldown update` or
`cargo cooldown add <crate>`. The policy is in `cooldown.toml`: a registry
version younger than seven days is refused, and versions already in the
lockfile are exempt. `cargo cooldown add` cannot set feature flags, so add the
crate plain, edit the features by hand, then run `cargo cooldown check`.

If your change adds or updates a crate and you do not have the tool, open the
pull request as it is and the maintainer will re-resolve the lockfile.

## Formatting

Rust is formatted with rustfmt's defaults. Run `cargo fmt --all` before a
commit; CI checks it. If a table is laid out by hand (grouped corpus strings,
for example), keep its layout with `#[rustfmt::skip]` on that item rather than
leaving the file unformatted.

## Tests

- **Unit tests live beside their file** as a sibling module: `foo.rs`
  declares `#[cfg(test)] mod tests;` and the tests are in `foo/tests.rs`.
- **Before a pull request**, run `cargo check --locked --workspace
  --all-targets` with zero warnings (CI sets `RUSTFLAGS=-D warnings`) and
  `cargo test --locked --workspace`. Neither needs anything installed; the
  shader compiler comes with the tree.
- **If you touched a shader**, run the conformance runner (`cargo run -p
  punchcutter-shape --example conform`) for shaping and the render example
  (`cargo run -p punchcutter-text --example render`) for coverage, and paste
  their summary lines into the pull request. If you changed a bound in
  `ot.slang` or `shape.slang`, also run `cargo run -p punchcutter-shape
  --example garbage -- --hostile` under lavapipe.
- **A test fixture must identify nobody.** Fixtures use invented data: no
  addresses, email addresses, keys or home paths.

## Logging

The library crates never print. What a load, a cover or a closure did goes to
`tracing`, once per event and never per frame or per glyph. A consumer that
installs a subscriber sees it. The examples print, because they are
harnesses.

## The public voice

Every comment and document is written for a reader who has never met the
authors and does not know the project's history:

- Explain the code as it is. No history ("used to", "previously", "moved
  from"), no personal or machine names, no dates as narrative, and no labels
  from anyone's private notes.
- Write plainly. Short declarative sentences, lists and commands rather than
  paragraphs that describe them, no aphorisms. Say what something does and how
  to run it.
- A comment that cites a document names its section, for example
  `docs/arena.md, *The merged glyph space*`. Never cite a section number, and
  never cite a document outside this tree. `docs/check-links.sh` checks every
  `docs/…md` pointer.

## Commits and pull requests

Stage files by name (`git add <file> <dir>/`), never with `git add -A` or
`git add .`, so that nothing reaches a commit by a wildcard. Keep commits
small and focused, with messages that say what changed and why. In the pull
request, describe what the change is, what you ran, and anything you found
but did not fix.
